# Release runbook: Shoprite switch-over, 20 October 2026

This runbook covers `7ec5051e1c` (the 13 October release) → the head of `main`: Shoprite orders into JRNY, Send Invoice, and the invoices flow. The general server commands come from `DEPLOY-RUNBOOK.md` in this folder.

The deploy itself is low risk:
- only the jrny and shoprite pieces change;
- there are no database migrations and no new pieces in `AP_DEV_PIECES`.

The risk is in the switch-over (sections 5–7). From then on, JRNYFLW acknowledges Shoprite orders and sends Shoprite invoices instead of the old platform.

**Run the live Shoprite flows in ONE environment only.** Pick the environment that has the JRNY **production** connection. Deploy the code everywhere, but import the two live flows only there.

## 1. What's in the release

| Change | Effect on a running environment | Action needed |
| --- | --- | --- |
| **Shoprite Download Orders** returns plain orders parsed from the GS1 document. | Breaks any flow that reads the old raw GS1 output. | Check for such flows (section 2). |
| **Shoprite Upload Invoice is removed** and replaced by **Send Invoice** (GS1 invoice XML, checked before sending). | A flow using Upload Invoice fails to load the step. | Check for such flows (section 2). |
| **Shoprite Acknowledge Orders** sends `action=Acknowledge` with the order numbers as XML. | Acknowledges for real. | Used only by the live orders flow (section 6). |
| **Shoprite connection: Supplier GLN and VAT Registration Number** (optional fields). | Send Invoice fails every invoice as `INVALID` without them. | Create a new Shoprite connection (section 4). Connections can't be edited yet. |
| **JRNY: Resolve Order Lines, Generate Pick, List Invoices Ready to Send, Record Invoice Result.** Create Quote gains Delivery Date, Auto-confirm, Idempotency Key and Portal Code. | New actions; existing steps are unchanged. | None. |
| **JRNY API description refresh** (96 operations). | New generated actions and filters. | None. |
| **Importable flows:** Shoprite orders (dev and live), Shoprite invoices, courier status sync. | Nothing until imported. | Sections 6 and 7. |

## 2. Before the deploy (workstation)

1. **Push `main`.** The servers pull from `origin`.
   ```bash
   cd ~/repo/jrnyflw && git checkout main && git log --oneline -1   # the commit that adds this file, or later
   CLAUDE_PUSH=yes git push origin main
   ```
2. **Look for flows using Shoprite Download Orders or Upload Invoice** in each environment you deploy to. Export each one as a rollback copy.
   - **Upload Invoice:** replace the step with Send Invoice after the deploy.
   - **Download Orders:** after the deploy, use Test step and re-point later steps at `output.orders`.

   If no flow uses the Shoprite piece yet, skip this.
3. **Check that these are ready.** Each item says what happens if it isn't.

   | Item | If it isn't ready |
   | --- | --- |
   | JRNY's next production deploy (`gtin` and `gtinSource` on invoice lines) | Every invoice is recorded `INVALID: … no Shoprite GTIN`. Leave the invoices flow off (section 7). |
   | GTINs loaded in JRNY as GTIN-type barcodes | Those lines are recorded `INVALID`. They self-heal on the next run after loading. |
   | Store GLNs on the SHOE100 delivery addresses | Those invoices are recorded `INVALID: Delivery address … has no GLN`. They also self-heal. |
   | The JRNY production key has `finance.delivery.write` | Record Invoice Result fails, and an invoice Shoprite accepted is sent again next run. Shoprite rejects the repeat, but JRNY never shows it as sent. **Don't turn the invoices flow on without this.** |
   | Supplier GLN and VAT registration number | Every invoice fails as `INVALID`. |
   | The first live invoice, agreed with AON | You have no known-good invoice to check against. |
4. **Agree a time with whoever runs the old platform.** It has to stop at the switch-over (section 5).

## 3. Backups (server, before touching anything)

```bash
cd ~/repo/jrnyflw
set -a && . ./.env.uat && set +a
docker exec jrnyflw-uat-postgres pg_dump -U "$AP_POSTGRES_USERNAME" "$AP_POSTGRES_DATABASE" \
  | gzip > ~/jrnyflw-pre-release-$(date +%F-%H%M).sql.gz
docker tag jrnyflw-uat:latest jrnyflw-uat:pre-2026-10-20      # instant rollback image
```

## 4. Deploy (server)

```bash
cd ~/repo/jrnyflw
git pull --ff-only && git log --oneline -1                 # the commit that adds this file, or later
grep '^AP_DEV_PIECES' .env.uat                              # unchanged: must still contain jrny and shoprite
DOCKER_BUILDKIT=1 docker build -f Dockerfile.uat -t jrnyflw-uat:latest .
docker compose --env-file .env.uat -f docker-compose.uat.yml up -d
curl -fsS http://127.0.0.1:${PORT:-3020}/api/v1/flags >/dev/null && echo READY
docker exec jrnyflw-uat-app grep -l send_invoice packages/pieces/custom/shoprite/dist/src/lib/actions/send-invoice.js
```

Then, in the builder:

1. In a new flow, the Shoprite piece lists **Send Invoice** and no longer lists Upload Invoice. The JRNY piece lists **List Invoices Ready to Send** and **Record Invoice Result**.
2. Fix any flow found in section 2.
3. **Connections → new Shoprite connection** with the production Base URL, Username, Password and Contract ID, plus **Supplier GLN** and **VAT Registration Number**. Name it clearly, for example "Shoprite production (invoicing)".
4. Check the **JRNY production** connection exists. Create it if not.

Do sections 5–7 only in the one environment that runs Shoprite live.

## 5. Switch-over (in this order)

1. **Old platform:** stop Shoprite order download and acknowledge, and stop invoice sending. Get confirmation that both have stopped.
2. **Dev orders flow:** if `shoprite-orders.flow.json` is imported anywhere, turn it off or delete it. Only one flow may read the Shoprite account.
3. Section 6 (orders), then section 7 (invoices).

## 6. Orders flow (live, acknowledges)

1. Import `docs/integrations/shoprite/shoprite-orders.live.flow.json` (new flow → Import).
2. Pick the connections:
   - **JRNY production** on steps 4, 15, 6, 8 and 10;
   - **Shoprite** on steps 1, 12 and 14.

   The file has placeholders, so every one must be picked.
3. **Test step 1** (Download Orders). It's read-only. Note the order count.
4. Publish and turn the flow on. To process the waiting orders now instead of at 08:00/16:00, use Run.
5. Check the run:
   - each order has a quote or sales order in JRNY with External Reference = the Shoprite order number and Portal Code `SHOPRITE`;
   - steps 12 and 14 ran for those orders with `ok: true`;
   - a second run downloads only the orders that weren't acknowledged.
6. An order with no loadable lines stays unacknowledged and comes back every run. Create it in JRNY by hand with External Reference = the order number and Portal Code `SHOPRITE`. The next run acknowledges it.

## 7. Invoices flow

Turn it on only once JRNY's production deploy and the `finance.delivery.write` permission are in place (section 2). Until then, leave it imported but off.

1. Import `docs/integrations/shoprite/shoprite-invoices.flow.json`.
2. Pick the connections:
   - **JRNY production** on steps 1, 7, 8 and 9;
   - **the new Shoprite connection** (with the GLN and VAT number) on step 5.
3. Check that step 1's **From Date** is `2026-10-20`. The old platform sent everything before it.
4. **Test step 1 only** (read-only). Read `count`, `clean`, `withProblems` and `waiting`.
   - `withProblems` invoices show what's missing in `problem`, such as a GTIN or a GLN. They'll be recorded `INVALID` in JRNY.
   - `waiting.notDelivered` invoices have no POD yet.
5. **First real invoice:**
   - set step 1's **Max Invoices** to `1`;
   - make sure the first clean invoice in step 1's output is the one agreed with AON;
   - run the flow once.
6. Check:
   - Shoprite has the invoice;
   - JRNY shows it **Sent**, with Shoprite's reference.
7. Set Max Invoices back to `50`, then publish and turn the flow on (hourly, 07:00–19:00).

What staff see in JRNY, and what to do, is in `docs/integrations/shoprite/invoices-flow.md`. Two things to know from the start:
- **`UNCONFIRMED`:** the invoice may be in Shoprite. It's never resent automatically. Check in Shoprite, then reset it in JRNY if it isn't there.
- **`REJECTED` because the invoice already exists:** Shoprite has it already. Mark it sent in JRNY, otherwise it's resent and rejected every hour.

## 8. The first days

- **Invoices dated just before 20 Oct.** Some were raised before the switch-over but delivered after it. If the old platform only sent invoices on delivery, neither system sends these. Check them by hand for the first few days.
- **Check each run in Runs.** The two outputs to read:
  - step 1 of the invoices flow: `withProblems` and `waiting`;
  - the orders flow: orders that come back unacknowledged.
- **An invoice whose dispatch never gets a POD** (a collection, own delivery or cancelled dispatch) waits forever. It shows only in step 1's `waiting.notDelivered`.

## 9. Rollback

**Code** (no database migrations in this release):

```bash
cd ~/repo/jrnyflw
docker tag jrnyflw-uat:pre-2026-10-20 jrnyflw-uat:latest
docker compose --env-file .env.uat -f docker-compose.uat.yml up -d
```

**Switch-over:**
1. Turn off both Shoprite flows.
2. Restart the old platform's order download and invoice sending.

Two things to check before restarting it:
- **Acknowledged orders don't download again.** The old platform won't see orders JRNYFLW has acknowledged, but those orders are already in JRNY.
- **Invoices JRNYFLW has sent show as Sent in JRNY.** If the old platform sends them again, Shoprite rejects them as duplicates.

## 10. Still open

- **Shoprite:** the exact text of a duplicate-invoice rejection. With it, the flow can mark those invoices as sent instead of retrying every hour.
- **JRNY:**
  - whether `fromDate` filters on the invoice date or on created_at;
  - production GTINs and GLNs.
- **Deferred:**
  - problem invoices are re-recorded every hour with no cap;
  - nothing stops two invoice runs from overlapping.
