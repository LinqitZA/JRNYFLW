## 1. What This Spec Delivers

A **single endpoint** that accepts a quotation create request, authenticated by a **bearer token**, scoped to a **single entity**. That's it. Everything else in the integration plan (`jrnyflw-integration-plan.md`) is deferred until this round-trip is confirmed working.

The smoke test the JRNYFLW side will run against this:

1. Generate a test bearer token in JRNY (manual SQL insert is fine for v0).
2. Configure a JRNYFLW connection with `{ baseUrl, entityId, entityCode, bearerToken }`.
3. Trigger a JRNYFLW flow with a static JSON payload.
4. Confirm a quotation appears in JRNY UI with the expected customer, lines, and total.

If this works, every other integration surface can be built on the same auth + path-scoping pattern.

## 2. Components Required on JRNY Side

### 2.1 API Key Model (minimum viable)

A table to store bearer tokens, scoped to a single entity per token.

```
core.integration_api_keys
─────────────────────────
id                UUID          PK
tenant_id         UUID          FK → core.tenants(id)
entity_id         UUID          FK → core.entities(id)        NOT NULL
fingerprint       TEXT          UNIQUE (last 8 chars of token, for display)
token_hash        TEXT          NOT NULL  (bcrypt or argon2 of the bearer token)
display_name      TEXT          NOT NULL  (e.g. "Smoke Test Key")
created_by        UUID          FK → core.users(id)
created_at        TIMESTAMPTZ   NOT NULL DEFAULT now()
last_used_at      TIMESTAMPTZ   NULL
revoked_at        TIMESTAMPTZ   NULL
```

For v0, **no UI** is required. A dev creates a key by:

```sql
INSERT INTO core.integration_api_keys
  (id, tenant_id, entity_id, fingerprint, token_hash, display_name, created_by)
VALUES
  (gen_random_uuid(), '<tenant-id>', '<entity-id>',
   'a1b2c3d4', '$argon2id$...', 'Smoke Test Key', '<user-id>');
```

The plaintext token is generated by the dev (e.g. `crypto.randomBytes(32).toString('base64url')`) and pasted into the JRNYFLW connection. It is **not** persisted in JRNY in plaintext form — only the hash.

Token format on the wire: `Authorization: Bearer <plaintext-token>`.

### 2.2 Bearer Token Guard

A NestJS guard that:

1. Reads `Authorization: Bearer <token>` from the request header.
2. Hashes the token using the same algorithm as `token_hash`.
3. Looks up the row in `core.integration_api_keys` by hash.
4. Rejects if: not found, revoked (`revoked_at IS NOT NULL`), or `entity_id` mismatches the `:entityId` path segment.
5. On success, sets `request.context = { tenantId, entityId, apiKeyId }` and updates `last_used_at` (async / fire-and-forget).

Guard name suggestion: `IntegrationBearerGuard`. Apply via decorator on the integration controller(s).

The guard **must** reject with `403 Forbidden` (not 401) when the token is valid but `entity_id` mismatches the path. This is the "hard gate" property of the Option A entity model.

### 2.3 The Endpoint

```
POST /api/v1/integration/entities/:entityId/quotations
```

#### Headers

```
Authorization: Bearer <token>
Content-Type: application/json
X-Idempotency-Key: <optional-uuid>   (recommended; see §2.5)
```

#### Request body

```json
{
  "customer": {
    "code": "ACME001"
  },
  "lines": [
    { "stockCode": "WIDGET-RED-LG", "qty": 10, "unitPrice": 199.99 },
    { "stockCode": "WIDGET-BLUE-LG", "qty": 5,  "unitPrice": 249.99 }
  ],
  "notes": "Smoke test from JRNYFLW",
  "externalReference": "FLOW-SMOKE-001"
}
```

**Resolution rules:**

- `customer.code` is resolved server-side to the customer's UUID within the path's `:entityId`. If not found → `400` with `error.code = "CUSTOMER_NOT_FOUND"`.
- `lines[].stockCode` is resolved server-side to the stock item's UUID within the path's `:entityId`. If not found → `400` with `error.code = "STOCK_ITEM_NOT_FOUND"` and `error.details.stockCode = "<offending-code>"`.
- `unitPrice` is in the entity's operating currency. Multi-currency support is deferred for v0.
- `externalReference` is stored on the quotation as `external_reference` (or whatever the existing field is) — used for idempotency and audit trail.

#### Success response — `201 Created`

```json
{
  "id": "01HX9JYZQ6P3R8VAW5T2KZGF7M",
  "quoteNumber": "Q-2026-00042",
  "status": "draft",
  "entityId": "<entityId>",
  "customerId": "<resolved-customer-uuid>",
  "totals": {
    "subtotal": 3249.85,
    "tax": 487.48,
    "total": 3737.33,
    "currency": "ZAR"
  },
  "createdAt": "2026-05-04T12:34:56.789Z",
  "links": {
    "self": "/api/v1/integration/entities/<entityId>/quotations/<id>",
    "ui":   "/sales/quotations/<id>"
  }
}
```

The `links.ui` field is what the JRNYFLW button-trigger UX (per integration plan §3.4) will render as a clickable success link.

#### Error response shape (all 4xx / 5xx)

```json
{
  "error": {
    "code": "STOCK_ITEM_NOT_FOUND",
    "message": "Stock item 'WIDGET-PURPLE' does not exist in entity 'ZA01'",
    "details": { "stockCode": "WIDGET-PURPLE" }
  },
  "requestId": "<uuid>"
}
```

**Error codes for v0:**

| HTTP | code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Body schema violation (missing field, wrong type) |
| 400 | `CUSTOMER_NOT_FOUND` | `customer.code` does not resolve in the entity |
| 400 | `STOCK_ITEM_NOT_FOUND` | A `stockCode` does not resolve in the entity |
| 400 | `INVALID_QUANTITY` | `qty <= 0` or non-integer where required |
| 401 | `MISSING_TOKEN` | No `Authorization` header or malformed |
| 401 | `INVALID_TOKEN` | Token not found or hash mismatch |
| 403 | `ENTITY_MISMATCH` | Token valid but entity in path ≠ token's bound entity |
| 403 | `KEY_REVOKED` | Token's `revoked_at IS NOT NULL` |
| 409 | `IDEMPOTENT_REPLAY_CONFLICT` | Same `X-Idempotency-Key` with different body |
| 422 | `BUSINESS_RULE_VIOLATION` | E.g. customer is on credit hold; quotation creation rejected |
| 500 | `INTERNAL_ERROR` | Anything unexpected; safe-to-retry guidance in `error.message` |

### 2.4 Implementation Notes for the JRNY Team

- The endpoint is a **thin adapter** over the existing `QuotationService.create()` (or whatever it's called). Do **not** reimplement quotation logic. The adapter's job is:
  1. Resolve `customer.code` → `customerId` (existing repository call, scoped to `entityId`).
  2. Resolve each `stockCode` → `stockItemId` (existing repository call, scoped to `entityId`).
  3. Call the existing service with a synthetic context: `{ userId: <api-key's created_by>, entityId: <from path>, source: 'integration_api' }`.
  4. Map the service's domain object to the response shape above.
- If `QuotationService.create()` requires a current-user UUID for audit, use the API key's `created_by` field. The audit trail thus records "created by integration key X (originally provisioned by user Y)" — this is the right behaviour.
- The endpoint **bypasses** any UI-layer permission checks (e.g. "user must have role X") — the bearer token is the authorization. But it **does not** bypass business rules (credit hold, fiscal period closed, stock not active, etc.) — those still apply.
- Place the endpoint under a new module: `apps/api/src/modules/integration/`. Don't pollute the existing `quotations` module with bearer-auth concerns.
- All input data is *external* — sanitise before storing. Use the existing `sanitizeObjectForPostgresql()` if applicable.

### 2.5 Idempotency (recommended for v0; required for production)

For v0, support is **optional** but **strongly recommended** because retries from JRNYFLW (after timeouts) are a real failure mode.

- Pseudo-table: `(api_key_id, idempotency_key, request_hash, response_body, created_at)`.
- On request: if `(api_key_id, idempotency_key)` exists with a matching `request_hash` → return the cached `response_body` with `200 OK`. If the hash differs → `409 IDEMPOTENT_REPLAY_CONFLICT`. If absent → process normally and persist.
- TTL: 24 hours is enough for v0.

If skipped for v0, document the gap so the JRNYFLW side knows duplicate quotes are possible on retry.

### 2.6 Observability

- Log every integration request with: `requestId`, `apiKeyId` (not the token), `tenantId`, `entityId`, `endpoint`, `status`, `durationMs`, `errorCode`. Standard structured-log shape.
- Emit a metric `integration_api_requests_total{endpoint, status}` for Prometheus.
- On 401/403, log the *first 4 chars* of the offending token to aid debugging without leaking secrets.

## 3. Test Setup the JRNYFLW Side Will Use

For the smoke test, the JRNY dev team needs to provide:

1. **A running JRNY dev instance** reachable from the JRNYFLW container's network (either same docker network or `host.docker.internal`-reachable).
2. **A pre-seeded entity** with at least one customer and two stock items. Suggested seed:
   ```
   Entity:    ZA01 (operating currency ZAR)
   Customer:  ACME001 — "Acme Corp"
   Stock:     WIDGET-RED-LG  (any tax category, any selling price)
              WIDGET-BLUE-LG (any tax category, any selling price)
   ```
3. **A test bearer token** issued via the SQL insert above, scoped to the seeded entity.
4. **The base URL** of the dev instance (e.g. `http://localhost:4200/api` or whatever the dev port is).

These four artefacts get pasted into the JRNYFLW connection form during the test. **Do not commit the bearer token to any repo.**

## 4. What Comes After v0 Passes

Once this round-trip works, the JRNY team adds (in roughly this order):

1. `GET /api/v1/integration/entities` — list entities the token can act on (needed for piece dropdown UX in V1.1).
2. API key management UI in JRNY shell, gated by `integration.manage_keys` permission.
3. Outbound webhook dispatcher (separate spec — for state-trigger use cases).
4. The remaining action endpoints: `POST .../sales-orders`, `POST .../receipts`, `GET .../debtors`, `GET .../stock-items`, etc.
5. Idempotency hardened to required.

None of these are needed for the smoke test. They become spec docs of their own.

---

## 5. Out of Scope (v0)

- Per-tenant HMAC signing keys (no outbound webhooks yet).
- Entity dropdown / discovery endpoint (token is bound to a single entity).
- API key CRUD UI (manual SQL insert is fine).
- RBAC permissions for key management (any DB-admin can issue keys).
- OpenAPI spec generation (worth doing once contract stabilises).
- Rate limiting (worth adding in v0.5).
- Multi-currency handling on quotation lines.

---

## 6. Acceptance Criteria for v0

The JRNY side is ready when **all** of the following are true:

- [ ] A bearer token can be issued via SQL insert and validated by the guard.
- [ ] `POST .../entities/:entityId/quotations` with valid bearer + valid body returns `201` with the documented response shape.
- [ ] An invalid bearer returns `401`.
- [ ] A bearer scoped to entity A, used against entity B's path, returns `403 ENTITY_MISMATCH`.
- [ ] An unknown `customer.code` returns `400 CUSTOMER_NOT_FOUND`.
- [ ] An unknown `stockCode` returns `400 STOCK_ITEM_NOT_FOUND` with the offending code in `details`.
- [ ] The created quotation is visible in JRNY UI under the seeded entity.
- [ ] The quotation's audit log records `source: integration_api` and the API key's `created_by` user.

When these are green, the JRNYFLW side runs the full smoke test (export, import, second-instance trigger).
